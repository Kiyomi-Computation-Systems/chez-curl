After M7 a caller can:

- ask for HTTP/1.1, HTTP/2, or HTTP/2 by prior knowledge over `http://` (ADR-0034);
- give a server credentials, and pick Basic, Digest or Bearer (ADR-0036);
- name an `http://` or `https://` proxy by URL, with credentials in its userinfo, and the proxy's
  own CA file and verification (ADR-0037);
- keep a session's cookies in a jar, and read them out and load them as data (ADR-0035).

- **The low level keeps its stand,** no policy (brief §6.1): each is a request key, and the jar
  is an engine's object. The high level carries them through a session and a call, and owns what
  is policy: whether a session keeps a jar, and dropping credentials across origins.
- **Caller code never runs on the engine's thread** (ADR-0012). The jar is made, read, loaded and
  freed there, by message.
- **Not in M7** (ADR-0033): NTLM, Negotiate, SOCKS, Digest at a proxy, cookie files, `PIPEWAIT`.
- **M7 has four slices:** the HTTP version; auth; proxies; the cookie jar.

## 2. Measured before planning (2026-11-02)

Four C probes, each stepping a multi handle as the engine does, ran on the five Linux libcurls,
two runs each: 7.85.0, Ubuntu's 8.5.0 with OpenSSL and with GnuTLS, Guix's 8.20.0 and 8.23.0.
Their stand-ins use Node's standard library alone. Each was an Opus agent's; I reran each one's
Guix lane, and its output matched the agent's (§10). The plan's review added a probe of its own
(§11). The Mac ran all four against Apple's 8.7.1 (§7).

- **HTTP/2 and the version** ([`research/m7/http2/`](research/m7/http2/)): unset and `NONE` act as
  `2TLS` on all five; `2_PRIOR_KNOWLEDGE` over `https://` offers `h2` alone on 8.20.0 and 8.23.0
  (no lane runs a version between 8.5.0 and 8.20.0), and fails 35 against an HTTP/1.1 origin
  there; `PIPEWAIT` shares a connection, but on 8.20.0 and 8.23.0 serialises requests to an
  HTTP/1.1 origin over TLS; ADR-0030's paused-stream bytes stand. ADR-0034 has the numbers.
- **Cookies** ([`research/m7/cookies/`](research/m7/cookies/)): a `curl_share` of cookies, with
  `COOKIEFILE ""` on each handle, carries them across fresh handles, live ones too, with no lock
  callbacks; read-out and load round-trip; the rules vary by version and PSL. ADR-0035 has the
  numbers. Also: a caller's `Cookie` header goes out as a second `Cookie` header beside the
  jar's, and `COOKIE` beside a caller's header is dropped; a cookie whose domain is `localhost`
  reached no `*.localhost` host in any case measured, by how libcurl buckets its jar (read in
  source), so a cross-host test uses three labels; libcurl resolves
  `*.localhost` itself, to `::1` first from 8.5.0.
- **Auth** ([`research/m7/auth/`](research/m7/auth/)): `USERNAME` and `PASSWORD` set both, with
  no URL userinfo, send the same bytes on all five; mixing them with userinfo varies; one scheme
  is one request for Basic and Bearer and a round for Digest; SHA-512-256 on 8.20.0 and 8.23.0
  alone; `auth-int` on a `POST` is broken everywhere; an HTTP/2 401 ends the transfer. ADR-0036
  has the numbers.
- **Proxies** ([`research/m7/proxies/`](research/m7/proxies/)): `no_proxy` beats `PROXY`; a
  caller's headers go to the origin inside a tunnel; the proxy's TLS is its own; GnuTLS 8.5.0
  stalls on TLS inside TLS; a refused `CONNECT` is 56 or 7 by version. ADR-0037 has the numbers.

## 3. Decisions that bind every slice

### 3.1 The public surface

New request keys, each unset by default, so a request that names none sets what it sets today
(ADR-0023, decision 3):

| Key | Value | Sets |
|---|---|---|
| `http-version` | `http/1.1`, `http/2` or `http/2-prior-knowledge` | `HTTP_VERSION` at `1_1`, `2TLS` or `2_PRIOR_KNOWLEDGE` |
| `credentials` | `(basic USER PASSWORD)`, `(digest USER PASSWORD)` or `(bearer TOKEN)`, each a string | `HTTPAUTH` at the scheme; `USERNAME` and `PASSWORD`, or `XOAUTH2_BEARER` |
| `proxy` | as today, `environment` or `#f`, or a URL string | `PROXY` at the URL, and `NOPROXY` at `""` |
| `proxy-ca-file` | a path | `PROXY_CAINFO`, and `PROXY_CAPATH` cleared |
| `proxy-verify` | `#t`, the default, or `#f` | `PROXY_SSL_VERIFYPEER` and `PROXY_SSL_VERIFYHOST` |
| `cookie-jar` | a jar of the engine the request is submitted to | `SHARE`, then `COOKIEFILE` at `""` |

- **Each key's options come from a pure settings function,** as the TLS fields' do from
  `tls-settings`: `version-settings`, `credentials-settings`, `proxy-settings` (`PROXY`, `NOPROXY`
  and the proxy's TLS) and `jar-settings` (`SHARE`, then `COOKIEFILE`). Each suite writes its
  function's answers out whole, for every value. A behavioural test cannot tell some of these
  apart: `http/2`'s `2TLS` acts as unset on every face, and a cleared `PROXY_CAPATH` as one left
  at its default where no store trusts the run's CA.
- **`http/2` maps to `2TLS`,** not `2_0`: over `http://` it sends HTTP/1.1 with no `Upgrade`,
  alike on all five, where `2_0` sends `Upgrade: h2c`, which no face accepts.
- **One key for credentials and their scheme,** so no scheme can be named without what it
  sends. The version symbols match the response's `http-version` values.
- **Every string a new key holds is copied, then checked, and the copy used** (AGENTS.md's
  mutable values): the `credentials` list and its strings, the proxy URL and `proxy-ca-file`, at
  construction and again at submit, as `request-checks` does for the URL and headers today. A
  test mutates each after construction and submits.
- **A refusal never carries a secret:** a refused password, token or proxy userinfo is named by
  its field, not its value, among a condition's irritants.
- **`proxy-ca-file` and `proxy-verify` are for an `https://` proxy URL alone.** Beside any other
  `proxy`, a `proxy-ca-file`, or `proxy-verify` at `#f`, is refused,
  `proxy-tls-without-https-proxy`; `proxy-verify` at its default is not. With an `https://` proxy
  and no `proxy-ca-file`, the proxy is verified against libcurl's default store, as an origin
  without `ca-file` is.
- **The jar** (§3.5): `make-curl-cookie-jar` takes an engine and answers a jar;
  `curl-cookie-jar-cookies` answers its cookies as a list of Netscape lines;
  `curl-cookie-jar-load!` takes such a list; `curl-cookie-jar-close!` closes it. Each is a message
  the engine's thread answers, and each waits with a bound.

The high level:

- **The session and the call take `http-version`, `credentials`, `proxy`, `proxy-ca-file` and
  `proxy-verify`,** a call's value replacing the session's, as today's request keys do. Each slice
  builds its keys at both levels.
- **A call's `proxy` takes the session's proxy TLS keys with it:** a call that names its own
  `proxy` drops the session's `proxy-ca-file` and `proxy-verify`, so a session's `https://` proxy
  settings never meet a call's `environment`.
- **Every new key reaches every hop:** `next-request` rebuilds a hop from a key list, so each
  slice adds its keys there and tests a redirect with each, the dropped one too.
- **Across a redirect to another origin, the high level drops `credentials`,** as it drops an
  `Authorization` header (the M5 plan; ADR-0036), the plan's own rule (§9, item 5).
- **A session takes `cookies`, `#f` by default:** `#t` makes a jar on the session's engine, which
  every call of the session carries, each hop of a redirect a fresh transfer on it, and which the
  session's close frees. A failed jar stops the engine the session made, and the construction
  raises. `http-session-cookies` reads it out; `http-session-load-cookies!` loads lines.

### 3.2 The HTTP version (slice 1; ADR-0034)

- **`http/2-prior-knowledge` with an `https://` URL is refused** at submit,
  `prior-knowledge-over-https`. At the high level, a redirect from `http://` to `https://` with
  it fails the call with that refusal, which a test holds and the documentation names.
- **Prior knowledge beside a named proxy is refused,** `prior-knowledge-through-proxy`: libcurl
  ignores it through a proxy that does not tunnel ("Ignoring HTTP/2 prior knowledge due to proxy",
  7.85.0 `http.c:3066`, 8.20.0 `http2.c:2875`, read in source). Beside `proxy environment` it is
  documented. Slice 1 measured both through the engine (ADR-0034, amended): ignored through a
  plain proxy on all five, the request HTTP/1.1 in absolute form; spoken inside a tunnel,
  `HTTPPROXYTUNNEL` at 1. No named proxy exists before slice 3, where no test of the refusal
  could fail, so slice 3 builds it, and decides `HTTPPROXYTUNNEL` with it.
- **No transfer sets `PIPEWAIT`,** and the hatch's `PIPEWAIT` stays allowed, documented.
- **Twins:** `HTTP_VERSION` becomes owned; the slice measures `SSL_ENABLE_ALPN`, which can turn
  `http/2` into HTTP/1.1, and `ALTSVC` and `ALTSVC_CTRL`, which can move a transfer to another
  version or host, and owns each that changes what the field sets, as `HSTS` was owned. Measured:
  `SSL_ENABLE_ALPN`, `ALTSVC` and `ALTSVC_CTRL` are owned, the last after the slice's review
  showed it moving a resend inside one transfer (ADR-0009, amended 2026-11-02).
- **The engine keeps not multiplexing on 8.7.x** (ADR-0030, amended).

### 3.3 Auth (slice 2; ADR-0036)

- **Every `credentials` string refuses NUL, CR, LF and each byte the header rule refuses,**
  `credentials-bytes`: libcurl writes a Bearer token raw into its header, and quotes a Digest user
  name escaping only `"` and `\`, so CR LF in either wrote a header of its own on the five lanes
  (8.23.0 percent-encodes the Digest name) ([review](research/m7/review/)). A Basic user name
  holding `:` is refused too (RFC 7617). Each rule is tested on bytes where it and its neighbours
  differ.
- **`credentials` beside userinfo in the URL is refused,** `credentials-beside-userinfo`, read
  from `curl_url`'s user and password parts. 7.85.0 reports no user for `http://@h/`,
  `http://:@h/` and `http://:p@h/`, where 8.5.0 and later report `""` (review), so those URLs pass
  beside `credentials` there; the table of §3.7 pins what each sends.
- **`credentials` beside a caller's `Authorization` header is refused,**
  `credentials-beside-authorization`: libcurl drops its own Basic and Bearer for the caller's, and
  sends both beside Digest (review). The high level's merge of a session's and a call's headers
  and keys is checked as the request is built.
- **A Digest `credentials` beside a streamed body or a streamed response is refused,**
  `digest-with-stream`, by a rule of its own: today's `stream-with-rounds` fires beside
  `stream-buffer` alone, so a `body 'stream` beside the hatch's `HTTPAUTH` passes today. With
  `HTTPAUTH` owned, `rounds-option-names` keeps `PROXYAUTH` alone, and test-stream's hatch
  `HTTPAUTH` rows become `owned-option` rows. Basic and Bearer are one request each, and a stream
  takes them.
- **Twins:** `HTTPAUTH`, `XOAUTH2_BEARER` and `AWS_SIGV4` become owned. `AWS_SIGV4` set after
  `HTTPAUTH` Basic replaced it with a signature on the five (review). The slice measures
  `LOGIN_OPTIONS`, `DISALLOW_USERNAME_IN_URL` and `UNRESTRICTED_AUTH`, and owns each that changes
  what the field sends.
- **The measurements reach owned options through a prototype,** a patch on a copy of `src/` that
  nothing ships, as M6's slices measured; the hatch cannot set `USERNAME` or `PASSWORD`.
- **The origin's Digest verifier is held to RFC 2617's and RFC 7616's published vectors and to
  planted failures,** as the probe's self-test was; whole-header assertions use challenges
  without `qop`, since libcurl's `cnonce` is random.
- **A wrong password ends with the server's 401 and code 0,** as any status does.
- **The slice measures `(basic "" "")`,** both empty, which no probe case held, and a UTF-8
  Digest user name by `USERNAME`, which 8.23.0 percent-encodes (review).

### 3.4 Proxies (slice 3; ADR-0037)

- **A proxy URL is parsed by `curl_url` and checked:** one it cannot parse is `proxy-url`; a
  scheme but `http` or `https` is `proxy-scheme`; a path but `/`, a query or a fragment is
  `proxy-url-parts`. **A URL that names no port gets its scheme's, 80 or 443,** set in the URL
  chez-curl hands `PROXY`, so every lane connects alike: 8.23.0 tries 80 where the rest try 1080
  (decided by the maintainer, 2026-11-02; ADR-0037, amended). Its userinfo is the proxy's
  credentials, sent by Basic on the first request, and held to `credentials-bytes`' rule.
- **A caller's `Proxy-Authorization` header is refused,** `proxy-authorization-header`, whatever
  `proxy` names: inside a tunnel it reached the origin. The high level's drop of it across origins
  becomes unreachable and goes, with its test rewritten as the refusal's.
- **`NOPROXY ""` with every proxy URL,** so no variable sends the transfer direct.
- **A `proxy-ca-file` is refused as a `ca-file` is** (ADR-0024), with `proxy-verify` on:
  `environment-override` on a Guix libcurl that loaded with `SSL_CERT_FILE` or `SSL_CERT_DIR` set,
  since the variable wrote over a set `PROXY_CAINFO` too; and `keychain-fallback` on Apple's
  LibreSSL, by analogy with the origin's: no probe has a proxy CA the keychain trusts.
- **An `https://` origin through an `https://` proxy is refused on Ubuntu's 8.5.0 with GnuTLS,**
  `proxy-tls-in-tls`, at submit: there it never finished, every run, its control passing, and
  without a bound it would wait for ever. The rule is keyed by version and backend, as 8.7.x's
  multiplexing rule is, and each libcurl the Mac or a lane measures joins the list or does not
  (decided by the maintainer, 2026-11-02; ADR-0037, amended).
- **A pooled tunnel and other proxy credentials:** 7.85.0 matches a pooled proxy connection by
  type, host and port alone (`url.c:935-944`), and 8.20.0 and 8.23.0 compare the user and
  password too (read in source). The slice measures, through the engine, whether a request with
  other proxy userinfo reuses an authenticated tunnel on each lane, and the Mac's; where it does,
  the transfer sets `FRESH_CONNECT` beside proxy userinfo.
- **A refused `CONNECT`'s status is in `HTTP_CONNECTCODE` alone:** on 8.20.0 and 8.23.0 a 407 is
  code 7, the connect class, which a retry policy repeats. The slice reads what the high level's
  retry does with each code, and ADR-0022's sent rule, `REQUEST_SIZE`, which counts a `CONNECT`
  on 7.85.0 alone; it amends ADR-0022 if a retry would act differently by version.
- **Twins:** `PROXY`, `NOPROXY` and the proxy TLS options a field sets are owned already; the
  slice owns `PROXYAUTH`, `PROXYUSERPWD`, `PROXYUSERNAME` and `PROXYPASSWORD`, and measures
  `HTTPPROXYTUNNEL`, `SUPPRESS_CONNECT_HEADERS`, `PROXY_SERVICE_NAME`, `SOCKS5_AUTH` and
  `HAPROXYPROTOCOL`, owning each that changes what a field sends. With `PROXYAUTH` owned,
  `stream-with-rounds` loses its last option and goes.

### 3.5 The cookie jar (slice 4; ADR-0035)

- **A jar is a record holding its engine, its share's address, a state and a holder count.** Its
  states are live, closing and closed. The engine counts the share as it counts every native
  object (ADR-0012), made and freed in one critical section with its count and its record.
- **Each transfer that holds a jar raises its count in `set-up!` and lowers it in `take-out!`.**
  `set-up!` checks the jar's state on the engine's thread, and fails the token
  `cookie-jar-closed` when it is not live; the check at submit is an early refusal only, since a
  close and a submit on two threads can cross.
- **A close sets closing,** and the engine frees the share when the count reaches zero, then marks
  the jar closed in the same section. The close answers at once; a transfer submitted after it is
  refused.
- **The jar's messages** (make, read out, load, close) are queued beside submits and taken in the
  order queued, so a load queued before a submit is in the jar before that transfer starts.
  `shut-down!` and `fail-engine!` answer every queued jar message, as they answer submits. An easy
  handle `fail-engine!` abandons keeps its share `CURLSHE_IN_USE`; the share is left with it, and
  counted as abandoned.
- **Order on each transfer:** `SHARE`, then `COOKIEFILE ""`. A load sets `COOKIELIST` on a handle
  the engine keeps for the jar's messages, attached to the share, so a load never meets a
  transfer's own handle. A read-out walks `CURLINFO_COOKIELIST`'s `curl_slist` there, and frees
  it with `curl_slist_free_all`.
- **A load takes Netscape lines alone,** each refused whole, `cookie-line`, unless it is seven
  fields, tab-separated, `#HttpOnly_` allowed, where no field holds a byte from 0x00 to 0x1F or
  0x7F, no field is empty but the value, and the path is not `TRUE` or `FALSE`. libcurl answers 0
  to a line it drops, and before 8.23.0 stores control bytes raw; 7.85.0's `strtok_r` merges an
  empty field; a CR cut a value on the five (review).
- **A read-out answers libcurl's lines as they are.** On 7.85.0 a cookie whose name or value holds
  a tab is listed as eight fields, which the load refuses (ADR-0035, amended): §3.7 pins it.
- **A request's `cookie-jar` from another engine, or not live, is refused** when submitted,
  `cookie-jar-engine` and `cookie-jar-closed`. Neither is a construction check.
- **Owned options:** `SHARE`, `COOKIE`, `COOKIELIST` and `COOKIESESSION` join `COOKIEFILE` and
  `COOKIEJAR`.
- **A caller's `Cookie` or `Host` header on a request with a jar is refused,**
  `cookie-beside-jar`, so one source holds a request's cookies: libcurl sends a caller's `Cookie`
  as a second header beside the jar's, and a caller's `Host` sets the host the jar matches cookies
  against, sending and storing (8.20.0 `http.c:2553`, `:3554`, read in source) (decided by the
  maintainer, 2026-11-02; ADR-0035, amended). At the high level a session with `cookies` refuses
  either in its headers or a call's.
- **Natives:** a `share` kind in `(curl private counters)`, written out where the kinds are
  (`test-memory-safety`, `test-curl-testing`), the owner registry's share handles, and a
  `curl_slist` ftype in `layouts` with its rows.

### 3.6 Refusals

Each has a reason symbol of its own, on `&curl-request-error`, raised where today's rules raise:
a request's own shape at construction and again at submit, and what needs the loaded libcurl or
the engine at submit alone. A wrong type is an assertion violation, as the house rule has it.

| Slice | Reasons |
|---|---|
| 1 | `prior-knowledge-over-https` |
| 2 | `credentials-bytes`, `credentials-beside-userinfo`, `credentials-beside-authorization`, `digest-with-stream` |
| 3 | `prior-knowledge-through-proxy`, `proxy-url`, `proxy-scheme`, `proxy-url-parts`, `proxy-authorization-header`, `proxy-tls-without-https-proxy`, `proxy-tls-in-tls` |
| 4 | `cookie-line`, `cookie-jar-engine`, `cookie-jar-closed`, `cookie-beside-jar` |

`test-conditions` and `test-request` write the reasons and the request keys out, and grow with
them. Each refusal is tested beside a neighbour that passes, on bytes where they differ.

### 3.7 What varies by version, and what is documented

Each is a per-version table in its suite, with a row for each of the five Linux libcurls and
8.7.1, taken from two runs, a missing row failing by name (ADR-0017's rule):

- **slice 1:** the codes of prior knowledge against an HTTP/1.1 server over `http://` (52 on
  7.85.0, 56 on 8.5.0, 16 on 8.20.0, 8.23.0 and 8.7.1, natively; under Valgrind 55 too, a race,
  so each row holds every code seen: ADR-0034, amended); two requests submitted in one batch by
  prior knowledge over `http://`, which share one connection on 7.85.0 alone;
- **slice 2:** the Digest algorithms each version supports; a UTF-8 Digest user name on 8.23.0;
  what 7.85.0 sends for the URLs whose empty userinfo it does not report;
- **slice 3:** the refused `CONNECT`'s code (56 or 7); the pooled tunnel's reuse; which builds
  stall an `https://` origin through an `https://` proxy, and so refuse it;
- **slice 4:** `Domain=localhost` by the PSL bit, and from `localhost` itself, host-only on 8.5.0;
  the default path; `Path=rel` and `Path=`, kept as given and sent everywhere on 7.85.0 and 8.5.0;
  the 400-day cap; `Max-Age=-1`; a deleted cookie still listed; a `__Host-` cookie with
  `Domain=localhost`, kept on 8.5.0; a tab in a name or value, eight fields on 7.85.0.

A table is keyed by version, but GnuTLS 8.5.0 and OpenSSL 8.5.0 differ in slice 3: its key is
the version and the TLS backend's name, as ADR-0024's table already keys by more than version.

## 4. Slice 1: the HTTP version

### 4.1 First, measure

- **Through the engine,** on the five Linux lanes: each `http-version` value, by the hatch's
